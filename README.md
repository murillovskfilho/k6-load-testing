# k6-load-testing

[![smoke](https://github.com/murillovskfilho/k6-load-testing/actions/workflows/smoke.yml/badge.svg)](https://github.com/murillovskfilho/k6-load-testing/actions/workflows/smoke.yml)

Load, stress and spike tests with [k6](https://k6.io) against a small parcel tracking API (Node.js + PostgreSQL in Docker). The suite finds a real bottleneck, the analysis below explains it, and the fix is measured with the same scenarios. Every number in **Results** is generated from the k6 output files in [`results/`](results/), not typed.

| | |
|---|---|
| System under test | [`api/src/server.ts`](api/src/server.ts): tracking history, parcel detail and scan-event endpoints for a fictional carrier |
| Data | 200,000 parcels and ~3,000,000 tracking events, seeded deterministically ([`db/init/002_seed.sh`](db/init/002_seed.sh)) |
| Scenarios | smoke, load, stress, spike ([`k6/`](k6/)), one shared traffic model ([`k6/lib/traffic.js`](k6/lib/traffic.js)) |
| Gates | p95 latency, error rate and checks as k6 thresholds; per endpoint, per stress step and per spike phase |
| Bottleneck | Missing index on `tracking_events.parcel_id` (a foreign key Postgres does not index for you) |
| CI | Every push: compose up, k6 smoke, thresholds fail the job ([`.github/workflows/smoke.yml`](.github/workflows/smoke.yml)) |

## Analysis

### What was measured

One traffic model, four load shapes. Each virtual user (VU) picks an action, waits 0.5 to 1.5 s and repeats: 78% read a parcel's tracking history, 15% read parcel detail, 5% post a scan event, 2% ask for a code that does not exist (a 404 is the expected answer and is not counted as an error). Every response is checked for content, not just status: the history must hold 5 to 50 events, the detail must carry a valid tracking code.

| Scenario | Shape | Question it answers | Gates |
|---|---|---|---|
| smoke | 2 VUs, 30 s | Does every endpoint answer correctly? | p95 < 300 ms, errors < 1%, checks 100% |
| load | ramp to 50 VUs, hold 3 min | Does expected peak traffic stay fast? | p95 < 500 ms, errors < 1% |
| stress | steps of 50, 100, 200, 300 VUs | Where does it break, and how? | p95 < 1.5 s, errors < 5%, also per step |
| spike | 5, then 150 VUs in 10 s, then 5 | Does it survive a burst, and recover after? | per phase; recovery back to the smoke bar |

The same scenarios ran twice, minutes apart, on the same database: once without the index (`npm run bench:before`) and once with it (`npm run bench:after`). Nothing else changed between the runs.

### What the numbers say

**The smoke test passed before the fix.** With two users the slow query costs tens of milliseconds, well under the 300 ms gate, so CI on every push would never have caught this bottleneck. Smoke proves the endpoints work; only sustained concurrency exposes the cost. That is the case for running load tests at all, and the reason the smoke gate is not a performance claim.

**Under load the hot endpoint collapsed and took the healthy one with it.** At 50 VUs the tracking history p95 went from milliseconds to seconds. Parcel detail, which only reads the small, indexed `parcels` table, slowed down by the same order of magnitude. Its own query stayed under a millisecond in `pg_stat_statements`; the time was spent **waiting for a database connection**. The API has a pool of 10 connections, and when every one of them is busy with a full table scan, every request waits in the same queue. One slow query became a site-wide slowdown.

**There were no errors at 50 or 100 VUs, only waiting.** Errors appeared from 200 VUs on. At that point a request can fail in two ways: the API gives up after waiting 5 s for a connection (`503 database_busy`), or k6 gives up after 10 s. This run does not split the error rate by cause (see *What I'd add next*). Latency stops growing at 10 s because that is where k6 gives up, so the before p95 and p99 in stress and spike are a floor, not the real figure.

**Throughput fell as well as latency.** The before runs sent far fewer requests in the same time. That is not less demand: a k6 VU waits for its response before it acts again, so a slow system receives less traffic. This hides part of the damage (see the closed-model note in the trade-offs).

**The spike recovered.** Once traffic dropped back to 5 VUs, latency in the recovery phase was back under the smoke bar even without the index, so the system did not keep a backlog after the burst. What failed was the burst itself: a fifth of the requests during the spike were errors.

**After the fix nothing came close to a threshold.** p95 stayed in single-digit milliseconds in every scenario, including 300 VUs, and no request failed. This suite did not find the fixed system's limit; see *What I'd add next*.

### Root cause

`GET /parcels/:code/events` runs two queries: find the parcel id by tracking code (indexed, fast), then

```sql
SELECT status, location, occurred_at FROM tracking_events
WHERE parcel_id = $1 ORDER BY occurred_at DESC LIMIT 50;
```

`tracking_events.parcel_id` is a foreign key to `parcels.id`, and PostgreSQL **does not index the referencing side of a foreign key**. Only the referenced primary key gets an index. Without one, Postgres answers "events for parcel X" by reading all ~3 million rows (a parallel sequential scan, about 27,000 pages per call in `results/before/explain.txt`) to return about 15 of them. On its own that is still only tens of milliseconds. Under concurrency, ten of those scans compete for the database's 2 CPUs and for memory bandwidth, so each one takes much longer than it does alone. They also hold all ten pool connections for that time.

How the cause was confirmed, not guessed:

1. **k6 per-endpoint series** showed the slowdown starting on the history endpoint, while the detail endpoint only slowed once the shared pool was saturated.
2. **`pg_stat_statements`** for the before suite shows this one statement as practically all of the database's execution time, with a mean per call under load far above its single-call time in `EXPLAIN`.
3. **`EXPLAIN (ANALYZE, BUFFERS)`** shows the `Parallel Seq Scan on tracking_events` and how many rows it filtered out to keep a handful.

### Fix

[`db/init/003_index_tracking_events_parcel_id.sql`](db/init/003_index_tracking_events_parcel_id.sql):

```sql
CREATE INDEX idx_tracking_events_parcel_id_occurred_at
    ON tracking_events (parcel_id, occurred_at DESC);
```

After it, the plan becomes a `Bitmap Index Scan` on the new index that touches a few dozen pages. The planner picks a bitmap scan plus a tiny sort over a plain index scan because one parcel's events are spread across the table (they were inserted in time order, as in production). Either way the cost no longer depends on table size. The `occurred_at DESC` column lets Postgres use the index for the sort as well when it prefers that plan (for parcels with many events).

On a live table this would be `CREATE INDEX CONCURRENTLY`, which avoids blocking writes during the build but cannot run inside a transaction and takes longer. Here the index is part of the init scripts, so a fresh `docker compose up` gets the fixed schema, and `bench:before` drops it on purpose to reproduce the original.

### Limits of a local benchmark

Read these numbers as **before against after on the same machine**, not as capacity figures for any real deployment.

- **The load generator and the system under test share one laptop.** Docker Desktop runs every container in the same WSL2 VM. CPU limits (db 2, api 1, k6 2) keep them from starving each other, but they still share memory bandwidth, the disk and the host's thermal limits.
- **No network.** k6 reaches the API over the Docker bridge, so there is no real latency, packet loss or TLS. Production latency would be higher in both runs.
- **One run per scenario.** There is no repeat, so there is no variance estimate. The before/after gap is three orders of magnitude, far beyond run-to-run noise, but small differences between rows (for example 3.1 ms against 3.9 ms after the fix) mean nothing.
- **Synthetic, uniform data and access.** Every parcel has 5 to 25 events, and k6 picks parcels uniformly at random. Real tracking traffic is skewed toward recent parcels, which would keep their pages in cache and make the unindexed version look somewhat less bad.
- **Warm cache, no background work.** The database had just been seeded, nothing else ran on it, and autovacuum had little to do.
- **The suite writes.** About 5% of requests insert events, so each run leaves a few hundred to a few thousand extra rows on ~3 million. That is negligible for these results, but it means two runs never see exactly the same table.

## Design decisions and trade-offs

- **A bottleneck that is real, common and provable.** A missing index on a foreign key ships to production all the time, because nothing fails and small test databases hide it. It is also checkable with standard tools (`EXPLAIN`, `pg_stat_statements`). I chose it over a synthetic `sleep()` or an N+1 loop because the root-cause step had to be evidence, not a story.
- **Closed model (VUs with think time) rather than a fixed arrival rate.** VUs behave like users: they wait for an answer before acting again. That makes the scenarios easy to reason about ("50 people on the tracking page"), but a slow system then receives less traffic, which understates how bad the before numbers are (coordinated omission). An open model (`ramping-arrival-rate`) would keep sending requests at a fixed rate and show an even steeper collapse. It is the first item in *What I'd add next*.
- **Thresholds per endpoint, per stress step and per spike phase, not just overall.** An aggregate p95 would have hidden the most useful finding, that the healthy endpoint degraded only because it shares the pool. The per-step and per-phase series show where the curve bends and whether the system recovers, which a single number cannot.
- **Correctness checks inside a load test.** Every response is validated (event count, tracking-code format, 201 on write, 404 on unknown codes). A fast `500` or an empty list must count as a failure, not as good latency.
- **A 10 s client timeout and a 5 s pool wait.** Without limits, a saturated system just gets slower forever and the run never ends. The limits turn saturation into countable errors. The trade-off is that before-fix latency is capped at 10 s.
- **The fixed schema is the default.** A fresh clone runs against the indexed schema, which is what CI checks. The broken version exists only inside `bench:before`, which restores the index when it finishes, even if a run fails.
- **Numbers come from files, not from me.** `scripts/report.mjs` builds the Results block from the k6 summaries, the saved query plans and `pg_stat_statements`. Run metadata (host, Docker, limits, k6 version, commit) is saved next to them in `run.json`.
- **k6 in a container, pinned.** Nobody has to install k6, and CI runs the same binary (`grafana/k6:1.0.0`) as the laptop.
- **CI runs smoke only, on a smaller seed.** Shared GitHub runners vary too much for load numbers to mean anything, and a 15-minute benchmark on every push would be noise and cost. The smoke job checks that the stack starts, that every endpoint is correct and that latency stays under a ceiling. The capacity runs are local and their results are committed.
- **Constrained containers.** Fixed CPU and memory limits make the before and after runs comparable and keep the laptop's 8 cores from hiding the problem. They are not a sizing recommendation.

## What I'd add next

- **An open-model stress test** (`ramping-arrival-rate`) to find the fixed system's real ceiling. 300 VUs with think time did not get close to it.
- **Errors by status code.** A k6 counter tagged with the status, so the report splits `503 database_busy` from client timeouts instead of reporting one error rate.
- **Repeated runs with a spread.** Three runs per variant, with the median and range in the report, so smaller changes than a missing index can be measured honestly.
- **Server-side metrics during the run.** Prometheus + Grafana (or k6's InfluxDB output) for pool wait time, active connections and database CPU over time, next to the k6 latency curve.
- **A performance budget in CI.** A short, fixed-rate load test on a dedicated or self-hosted runner, gating merges on p95 against a stored baseline, not just on a fixed ceiling.
- **Soak test.** An hour or more at steady load to catch slow leaks, table bloat and autovacuum effects that a few minutes cannot show.

## How to run

Needs Docker and Node.js 20+. Nothing else: k6 runs in a container.

```bash
npm run up              # build the API, start Postgres, seed ~3M rows (about a minute the first time)
npm run bench           # smoke, load, stress, spike against the current schema -> results/latest/
```

Reproduce the before/after comparison and regenerate the tables above:

```bash
npm run bench:before    # drops the index, runs all four scenarios, restores the index
npm run bench:after     # same scenarios with the index
npm run report          # rewrites the Results block and results/REPORT.md from the JSON files
```

Single scenarios: `npm run smoke`, or `node scripts/bench.mjs --only load`. `npm run reset` removes the database volume, so the next `npm run up` seeds from scratch. A smaller dataset: `SEED_PARCELS=20000 npm run up` (as in CI).

## Layout

```
api/                      the system under test (Fastify + pg), built into its own image
db/init/                  schema, deterministic seed, and the fix (003_index_...sql)
k6/lib/traffic.js         traffic mix: 78% tracking history, 15% detail, 5% writes, 2% unknown codes
k6/lib/common.js          shared thresholds and the summary export
k6/{smoke,load,stress,spike}.js
scripts/bench.mjs         runs a variant end to end and saves the evidence
scripts/report.mjs        builds the Results tables from results/*/*.json
results/before|after/     k6 summaries, EXPLAIN ANALYZE, pg_stat_statements, host and run metadata
```
